You are helping me develop a teaching-grade mobile application for a Level 7 university module:

7CS123 – Advanced Software Engineering.

The application will be called:

UniPlanner

The purpose of this application is to provide a simple university student planning system. It will be developed progressively over six teaching weeks and will be used as the central example throughout lectures and workshops.

IMPORTANT:
This is an educational project, not a commercial production application. The code must be understandable to students who may have little or no previous mobile application development experience.

The application must therefore be:

* simple enough to explain in lectures
* realistic enough to demonstrate advanced software engineering
* modular
* well documented
* easy to extend
* easy to test
* suitable for demonstrating refactoring and design patterns
* suitable for Git and CI/CD
* deliberately structured so that students can see the difference between poor and good software engineering

TECHNOLOGY

Use:

* Android Studio
* Kotlin
* Jetpack Compose
* Android Jetpack
* MVVM architecture
* Repository pattern
* Kotlin Coroutines where appropriate
* standard Android testing technologies
* Git/GitHub-compatible project structure

Do not introduce unnecessary frameworks or libraries unless there is a clear educational reason.

APPLICATION DEVELOPMENT ROADMAP

The project must be designed to evolve through six teaching weeks.

WEEK 1 – MOBILE FUNDAMENTALS

Create a very simple working mobile application.

Focus:

* project creation
* Compose UI
* screens
* components
* navigation
* user interaction
* basic state

Do not introduce complex architecture yet.

The initial application should have:

* Dashboard
* Modules
* Assessments
* Profile
* basic navigation
* sample/local data

WEEK 2 – ARCHITECTURE

Refactor the application to introduce:

* MVVM
* View
* ViewModel
* Model
* Repository
* separation of concerns

Ensure that UI components do not contain significant business logic.

Clearly separate:

* presentation
* application logic
* data access

WEEK 3 – DESIGN PATTERNS AND SOLID

Extend the application and demonstrate appropriate design patterns.

Use only patterns that provide genuine value.

Consider:

* MVVM
* Repository
* Observer/reactive state
* Factory where appropriate
* Dependency Injection where appropriate

Apply SOLID principles.

The code should contain examples that can be discussed in a Level 7 Advanced Software Engineering lecture.

WEEK 4 – REST API AND DATA INTEGRATION

Introduce a backend/API abstraction.

The application should communicate with a REST API.

Implement appropriate operations such as:

GET modules
GET assessments
POST assessment
PUT assessment
DELETE assessment

Use JSON.

Implement:

* loading state
* success state
* empty state
* error state
* network failure handling

The Repository must hide the details of the data source from the ViewModel.

WEEK 5 – TESTING, BAD SMELLS AND REFACTORING

Introduce tests for:

* business logic
* validation
* ViewModel behaviour
* Repository behaviour where appropriate

Include examples of:

* valid input
* invalid input
* API/data failure

The project should also contain examples that allow students to identify common bad smells, such as:

* large class
* long method
* duplicate code
* tight coupling
* inappropriate responsibility

Provide a clean refactored version and clearly document what was changed and why.

WEEK 6 – PROFESSIONAL SOFTWARE ENGINEERING

Prepare the project for:

* Git
* GitHub
* meaningful commits
* branching
* pull requests
* code review
* CI
* automated testing
* build verification
* Agile development

Create a suitable README explaining:

* application purpose
* architecture
* project structure
* design patterns
* testing
* how to run the application
* development workflow

TEACHING REQUIREMENTS

For every major component, provide comments and documentation explaining:

* what it does
* why it exists
* which software engineering principle it demonstrates
* which design pattern it represents, if applicable
* how students could test it

Do not over-comment obvious code. Comments should explain design decisions rather than simply translating code into English.

ARCHITECTURE DOCUMENTATION

Create:

1. system architecture diagram
2. application component diagram
3. MVVM diagram
4. data flow diagram
5. API interaction diagram
6. project folder/package structure explanation

The diagrams should be suitable for use in university teaching slides.

TEACHING MODE

This application will be used to teach students who may have no prior mobile development experience.

Therefore:

* avoid unnecessary complexity
* use consistent naming
* keep classes reasonably small
* avoid magic numbers and unexplained configuration
* provide clear error messages
* make the UI visually clean
* use realistic sample data
* make each weekly version runnable

IMPORTANT DEVELOPMENT RULE

Do not make major architectural changes without explaining:

1. the problem with the current approach
2. why the new approach is better
3. what software engineering principle is being applied
4. what trade-offs exist

Create the application in a way that supports a teaching narrative:

Problem → Design Decision → Implementation → Testing → Refactoring → Improved Design

Before making changes, inspect the existing project and preserve working functionality.

At the end of each development stage, ensure the application builds and runs successfully.

Also provide a short “Teaching Notes” document explaining what I, as the lecturer, should demonstrate to students at each stage.
